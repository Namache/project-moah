# MCP integration

Project Moah exposes a local MCP server so coding agents can read project state and record their work. It runs over standard input and output, needs no network, and shares the app's database.

## Documentation checked before building (2026-10-10)

| Topic | Source | What was relied on |
| --- | --- | --- |
| Claude Code | https://code.claude.com/docs/en/mcp | `claude mcp add --transport stdio [--scope project] <name> -- <command> [args]`; `.mcp.json` with `mcpServers.<name>` `{type, command, args}`; `claude mcp list` and `/mcp` to verify. |
| Codex | https://developers.openai.com/codex/mcp | `codex mcp add <name> -- <command> [args]`; `[mcp_servers.<name>]` with `command`, `args`, `startup_timeout_sec` in `~/.codex/config.toml` or a trusted project's `.codex/config.toml`; `codex mcp list` and `/mcp` to verify. |
| Python SDK | https://pypi.org/project/mcp/ and the installed package | `mcp` 2.3.0 (Python 3.10+). v2 uses `from mcp.server import MCPServer`, `@server.tool(annotations=ToolAnnotations(...))`, `server.run("stdio")`, and `ToolError` for messages the agent should see. The older `FastMCP` name is not used. |

Vendor syntax is isolated in `frontend/src/content/integrations.ts` (the commands shown in Help and Settings). The server itself is in `backend/app/mcp/`. A vendor change should only touch the first.

## Starting the server

Installed app (Flatpak), what an agent runs:

```bash
flatpak run --command=project-moah-mcp io.github.projectbrain.ProjectBrain --agent claude --project trailhead
```

From source: `python -m app.mcp --agent codex --project trailhead` inside `backend/`. `--agent` names who is connecting (`claude`, `codex`, or anything else, recorded as system). `--project` sets a default project; without it the agent must pass one, or the working folder must match exactly one project's repository folder.

## One connection per agent (2026-10-11)

Each agent is connected once, for every project, without `--project`. The Connect button in Help and `project-brain-backend --connect` (`backend/app/services/agent_connect.py`, also reached through `project-moah-mcp --connect`) write all of this in one step (the Flatpak's sandbox can't, so its Help gives `flatpak run --filesystem=home --command=project-moah-mcp io.github.projectbrain.ProjectBrain --connect`, which may write the home folder for that one run); they replace an old `project-brain` entry, keep other settings, save a `.moah-backup` of each file they first change, and can be run again. An agent following [INSTALL.md](../INSTALL.md) uses them.

- Claude Code: user scope (`claude mcp add --scope user project-moah -- flatpak run --command=project-moah-mcp io.github.projectbrain.ProjectBrain --agent claude`), plus a `SessionStart` hook in `~/.claude/settings.json` that runs `project-brain-mcp --brief --cwd "$CLAUDE_PROJECT_DIR"`. Hook output becomes session context, so the brief costs no tool call. The hook also stores the session id Claude Code hands it (with the project), and the MCP server stores each task that session works on (it learns the session from CLAUDE_CODE_SESSION_ID; a Flatpak started from a container, such as distrobox running `flatpak` on the host through host-spawn, gets none of Claude Code's environment, so Connect writes the Flatpak's entry as `sh -c 'exec flatpak run ... --session-id "${CLAUDE_CODE_SESSION_ID:-}"'`, which hands the id over as an argument; without it the turn hooks can't tell which task a reply in the chat answers), so the Usage page matches token use in that session's log to tasks by id (`backend/app/services/agent_sessions.py`). Each context pack in Claude Code's log is also measured against the token jump it caused, which calibrates the Claude token factor (`backend/app/services/token_calibration.py`). Only ids, times and counts are kept.
- Codex: `[mcp_servers.project-moah]` in `~/.codex/config.toml`, and a line in `~/.codex/AGENTS.md` asking it to call `brain_brief` first, plus the same two turn hooks as Claude Code in `~/.codex/hooks.json` (Codex runs them once the person trusts them with `/hooks`).
- Turn hooks (Claude Code and Codex, `backend/app/services/chat_questions.py`): `Stop` runs `project-moah-mcp --agent <agent> --hook stop` and `UserPromptSubmit` runs `--hook prompt` (in Claude Code with `async: true`, so the message is not held up). Both read the hook's JSON on standard input, print nothing and always exit 0. Agents ask in the chat rather than with `brain_ask_person`, so `stop` records the question a turn ends on (the trailing paragraphs that ask something, from `last_assistant_message`, else the transcript's last assistant text) through the same path as `brain_ask_person`: the task moves to Blocked and the question waits in Review, with the rest of the message as its context and a short list under it as answer options. It needs the session's task: the newest one its MCP server recorded, else the task a message from the person named by ID or plainly by title (the context pack's rules, `_infer_task`, over To do and Backlog too, without the brief fallback) while the session had none. Nothing is caught without a task, once the task is in Review (an offer after a hand-over), for a turn that only asks "Anything else?" and the like, or when the agent asked with `brain_ask_person` in the same turn. A question on a task the person already closed (accepted or archived) waits in that task's follow-up, as with `brain_ask_person`, and the session goes on in the follow-up. `prompt` records the turn (by time; and while the session has no task, the task the message names), and settles a question waiting for the session's task with the person's message as the answer, `moved_to = "chat"`: shown as answered in the chat, left out of the brief's ANSWERED IN REVIEW (the agent has it), and `brain_get_task` says it was answered in the chat. Prompt records are not used for token use per task.
- Claude desktop app, Chat tab: `mcpServers.project-moah` in `~/.config/Claude/claude_desktop_config.json`.

The project comes from the agent's working folder, compared as path text (`/var/home` and `/home` are one spelling), so a folder the sandbox cannot open still matches. A project's folders are its own folder and every folder Sync from agents linked to it or created it from; when none holds the working folder, a folder in the same Git repository does (the `origin` remote, read from the repository's config file; Git is not run). When nothing matches, the brief says why if Project Moah knows: an ignored folder, one waiting for the person's answer, an archived project, or a temporary folder. Outside every project the brief carries only the Global rules. Each brief also runs **Sync from agents**: the folders Claude Code and Codex sessions start in become projects (temporary folders, worktrees and Codex one-off chats skipped); a folder whose name resembles an existing folderless project is asked about on the Projects page, never guessed; a folder named like one chosen for a project through the Flatpak file picker (a `/run/user/<id>/doc/` path, which hides where the folder is) is linked to that project.

## Tools

Second opinion: `brain_second_opinion` (off until switched on in Settings, Agents; returns a read-only command for the asking agent to run in its own terminal, so the person approves it there; Project Moah never starts an agent itself). Read-only: `brain_brief` (see "What the brief holds" below; it also runs Sync from agents; `update_steps=true` returns only the steps to install an update on this system, without starting a new session), `brain_list_projects`, `brain_project_state`, `brain_context_pack` (without `task`, the pack uses the session's task when it has one, so a question asked in the middle of a task stays on that task; else the project's focus; else an open task the query names by ID; else the task in progress, blocked or in review whose title and tags cover at least half of the query's meaningful words, share at least two of them (one, for a one-word request) and cover more than any other task does; else, for a bare "Continue.", the unfinished task the brief shows; the pack then says which task it used, and that task becomes the session's task; records named by ID in the task's unfinished criteria, its next action or its latest checkpoint's remaining work, problems and next steps come first, and every record the brief lists as already decided for the task (`brief_decided` in `brief.py`, the same selection) is in the pack whatever the detail level and section limits, with its text at balanced and detailed and by title at minimal; memory hidden from agents never comes; with a task, a decision, fact, note or idea whose only tie is a shelf woken by one keyword is left out; `operation` is detected from the task when omitted; agents' packs leave out the awake shelves and recent activity, which `explain=true` adds back with why each record came in, what was left out, the pack's size and the kind of work; Global rules are left out because every brief gave them; project rules come in full like any other record, since the brief lists them by title only; when the brief of the project this session's brief covered (the project of its last `brain_brief`, else the folder the client started the server in: the start-up hook's brief) showed the task's latest checkpoint under UNFINISHED, the checkpoint's remaining work reads "as in your brief"; `global_rules=true` puts all of it back; the checkpoint's next step is left out when it is the task's next action; a minimal pack still keeps the warnings and open bugs that match the work; the pack ends with its retrieval id in a `brain_retrieval_feedback` call; the same request gives the same pack unless "Let packs explore" is on in Settings, Agents; a repeat request in one session sends only what is new or changed and names the records the agent already has, or just "Nothing new since R-..."; `full=true` sends everything again; the server forgets what it sent on `brain_brief`, after 2 hours idle, and whenever Claude Code's start-up hook runs (session start, `/clear`, compaction)), `brain_get_task` (with the task's latest review round, when it has one), `brain_view_images` (the pictures a person attached to a task or memory record, or to their comment on a review, returned as MCP image content; records with images list them under `images`, and context packs note them as `[1 image attached: brain_view_images PROJ-6]`; memory hidden from agents is refused), `brain_list_tasks`, `brain_search` (every word must match; when no record has them all, it returns the 5 best records with any of them, without their status, and says `matched: any word...`, so a plain question such as "which day does the week start" still finds "Weeks start on Monday"; results carry the project's name only for `scope="all"`), `brain_get_related`, `brain_changed_files`, `brain_links` (what a record connects to, each link read from that record), `brain_shelves` (shelves, their members, and how strongly a task wakes each), `brain_link_review` (candidate links nobody has confirmed, orphan memory nothing links to, the graph's health, and shelves the brain suggests growing or merging).

Update check: once a day (local date), the first `brain_brief` (or, if no brief came first, the first `brain_context_pack`) ends with an UPDATE CHECK block: the installed version and how the agent can look up the latest GitHub release of Namache/project-moah with its own tools, then ask the person before updating. The install steps for this system (download, install, restart) are not in it: after the person says yes, the agent gets them with `brain_brief(update_steps=true)`, which keeps the session's task and packs. If it cannot reach GitHub it says one sentence ("Couldn't check for Project Moah updates, the machine is offline."). Project Moah itself makes no network call. Switch it off in Settings, Agents ("Automatically check for updates", on by default).

### What the brief holds

The start-up hook and `brain_brief` print the same brief (`backend/app/services/brief.py`). It is read in every session, so it stays short:

- **Global rules** in full, then the titles of all the project's **rules** (a context pack sends a rule's full text when the work needs it) and its locked or pinned decisions and warnings.
- **The unfinished task**: the focus task; else the task of the latest checkpoint that has a task, while that task is in progress or blocked (a checkpoint with no task, such as a small edit, does not hide it; a task parked in the backlog or todo, or finished and waiting in review, is not shown); else the only task in progress. With several tasks in progress and no such checkpoint it shows none rather than guess. Under it come the titles of what is already decided for it (active decisions, rules, warnings, facts and open bugs linked to the task by an active link, or named in its latest checkpoint, its next action or its open acceptance criteria; at most 6, records already listed above left out, and so are records a person linked to the task as unrelated, such as `independent_of`, or as contradicting it), what its latest checkpoint left to do (or, when it left nothing written, its next step, else the task's next action), and the exact `brain_context_pack(task="...", query="<the request>")` call. Showing the task changes nothing: the focus and the session's task stay as they are. A context pack asked to just "continue" uses the same task.
- **The latest checkpoint**, only when there is no unfinished task or the checkpoint is about another task.
- **Sent back from review**: up to 3 tasks the person sent back from the Review screen that no agent has submitted again, each with the start of the person's comment and how many files came with it. **Answered in review** does the same for tasks whose question the person answered.
- **Waiting for the person's review**: how many tasks are in review, how many agents' questions wait for an answer, and how many proposals are pending, when there are any.
- **How to work with Project Moah**: check Moah before asking the person anything, since their earlier answers are recorded there; when to fetch a context pack (generated from `RETRIEVE_WHEN`, which the retrieval benchmark replays); that writing records and checkpoints needs no permission (skipping trivia, and linking only real relationships); a checkpoint after task work, naming the records that helped, which is the pack's feedback; and that global rules, global decisions and locked records go to the person as proposals, while a finished task goes to them with `brain_submit_review`.

The MCP server's own instructions (in every client's system prompt) only say to call `brain_brief` when no brief is in context, to check Moah before asking, that writing records and checkpoints needs no permission, what needs the person's review, that each request, however small, is a task of its own handed over with `brain_submit_review`, and to ask with `brain_ask_person` when the agent stops for the person's answer.

Writes: `brain_create_task`, `brain_update_task` (status `review` or `completed` moves the task to review; without a report from the agent, the Review screen shows one Moah drafts from its checkpoints since the person last decided on the work (an answered question halfway through does not count), and the answer asks for `brain_submit_review`), `brain_archive_tasks` (archives tasks, or restores them with `restore`, only when the person asked: `person_asked` carries their words, which each task's history keeps; `all_done` archives every Done task of the project; a restored task goes back to Done if it was Done, to Backlog if it was in Backlog, otherwise to To do; at most 200 tasks a call; without the person's request, archiving stays a proposal), `brain_archive_memories` (the same for rules, decisions and other records, Global rules included, only when the person asked: `person_asked` carries their words; locked records are skipped and stay the person's), `brain_create_checkpoint` (a checkpoint that waits for the person, said with `waiting_for_person` or read from a title such as "mockup ready for review" or "waiting for the owner's OK", opens a question for its task in the Review screen and moves the task to Blocked; later waiting notes update that one question, and the next note that does not wait settles it as answered in the chat and takes the task back to in progress; handing the work over instead (`brain_submit_review`, or status `review`) replaces the question, since nobody answered it; a waiting note with no task starts one, tagged `started-by-moah`, which the session keeps; a waiting note on a task the person already closed (accepted or archived) goes to that task's follow-up, an open task Moah starts for it ("Follow-up to CAMP-001: ...", in progress, tagged `started-by-moah` and `follow-up`, related to it; one at a time per task, reused until it is closed too), and the result says so in `task_started`; without `task`, it reports on the session's task; a session with no task, which worked from the brief alone, reports on the brief's unfinished task when the checkpoint names that task or a record the brief lists as decided for it, and the result says so in `task_note`; records of the session's packs that its summary, completed work or next steps name count as useful feedback, each for the latest pack that held it; the result says which), `brain_create_memory` (with `related`, `tasks` and `shelf`; without one, the record is filed on the deepest shelf its words name, and so is a new task; the answer lists `possible_duplicates`, up to 3 active records of the same type whose titles share at least two meaningful words with the new one's title (its only one, for a one-word title; words in the content do not count), with a hint to update or supersede one instead when it already says the same), `brain_link_memories`, `brain_update_memory`, `brain_supersede_memory` (a rule's title can be at most 120 characters and its text at most 1,200, counted without leading and trailing spaces, on creating, editing, replacing and proposing one; a rule written before these caps keeps its length and may be shortened, never lengthened), `brain_create_proposal` (a `complete_task` proposal no longer waits as a suggestion: it moves the task to review like `brain_update_task`), `brain_submit_review` (hands a finished task to the person: a summary, what was done, what was not, how to check it, optional Markdown details, and up to 10 screenshot files with captions; the task moves to review and waits in the Review screen; submitting again replaces a round still waiting; in the Flatpak, which cannot read the agent's folders, screenshots are read from Moah's own `review-files` folder, which the tool's description names, and removed there once stored), `brain_ask_person` (asks the person something only they can answer, also when the agent asks in the chat, so the question is not lost; with optional Markdown context and up to 6 answers to pick from; the task moves to Blocked and the question waits at the top of the Review screen until the person answers; a question about a closed task waits in its follow-up, as for a checkpoint, and the result says so in `task_started`; the answer then shows in the brief, in `brain_get_task` and in a prompt the Review screen can open in Claude Code or Codex, and the task is back in progress; `brain_update_task` with status `blocked` and no question asks for one; an agent that moves the task on, or asks again, withdraws the question), `brain_link` (a typed link between two records; agents cannot remove a link a person made), `brain_update_shelf` (file records on a shelf, or create, change or delete one; a shelf is a name or a path such as "Knowledge > Software engineering > Frontend", and `shared` puts a new one on the shared tree every project files on, where each project sees only its own records), `brain_retrieval_feedback` (name the records of a pack that helped and the ones that were noise; a checkpoint naming the records that helped already counts them; a verdict counts once per agent session, in that pack or another of its packs, and a changed verdict on the same pack moves the record's count instead of adding one; links learn per kind of work, a useful record the pack missed gets linked to the task, and a guessed link between two records that both helped is confirmed).

### How writes join the Brain

Every write links the record as it is saved, so nothing an agent records stays an orphan:

- **What the agent names.** `brain_create_memory` takes `related` (any record: memory, a task, `file:src/a.gd`, `global:RULE-3`) and `tasks`. The memory, task and update tools take `links`, each written `"relationship target"`, for example `["caused_by DEC-002", "depends on CAMP-3"]`. A name that matches nothing is reported in `not_linked` and the record is still saved; it used to fail the whole write.
- **What the text names.** DEC-004, a file with notes, or `global RULE-3` in a title, content, description or next action becomes an active `references` link. This runs on edits, replacements and checkpoints too, not only on creation. Records with similar titles become candidate links, which are never followed until confirmed.
- **The session's task.** Each MCP server process serves one agent session and remembers the task it works on: the task of its last context pack (the task named; with none named, the session keeps its task; a session with no task yet takes the one the query names or plainly continues, or the focus task, but not for a search-only pack), a task set to `in_progress`, or the task of its last checkpoint. A record written without naming a task is linked to it (`relates_to`, active, confidence 0.6, "written while working on CAMP-3 in the same session"); a task created meanwhile is linked to it too; a checkpoint without a task reports on it, and the records the checkpoint names are linked to that task. `brain_brief` starts a new session and forgets the task (not with `update_steps=true`), and so does a pause of two hours between tool calls. The unfinished task the brief shows does not become the session's task by itself. `brain_project_state` shows the session's task and each pack ends by naming it. Limitation: Claude Code keeps the server running across `/clear`, so a record written after `/clear` but before the next context pack can still be linked to the previous task, within those two hours; reject such a link in the Brain or with `brain_link(remove=true)`. The task lives in the server's memory, so a server the client restarts mid-session forgets it, and records are linked to no task until the next context pack. A client that runs one server for several chats gives them one shared session task.
- **Replacing memory keeps its links**: tags, tasks, memory links, file notes and typed links all move to the new record.

The app asks the backend for a change counter (`GET /api/brain/version`) every four seconds while its window is visible, and refreshes what is on screen when the counter moves (the Brain, tasks, memory, reviews), so records and links an agent makes appear while you watch.

Each tool states whether it only reads. Errors are plain sentences that say what to do next.

## Agents inside a container (distrobox, toolbox)

Checked with an agent inside a distrobox container on an immutable Fedora-based desktop: the container's `flatpak` is a forwarder to the host, and the MCP connection works through it, including standard input and output. What the agent can see and what Project Moah can see differ, though:

| View | Path to the same folder |
| --- | --- |
| Inside the container | `/home/you/project` |
| On the host | `/var/home/you/project` (`/home` is a link to it) |
| Inside Project Moah's Flatpak | nothing, until shared |

The sandbox has the same `/home` link, so once a folder is shared, both spellings resolve and no path translation is needed. Share it with the Choose folder button, or read-only with `flatpak override --user --filesystem=<folder>:ro io.github.projectbrain.ProjectBrain` (undo with `--nofilesystem=<folder>`). Verified with a temporary grant: only that folder appeared, and writing to it failed. Until a folder is shared, the Git status is `not_shared`, with a message that says how to fix it, and everything else works. Pass `--project` in the setup command, as the guides do, because the container's working folder is not visible to the app and cannot be matched.

## Rules the server enforces

- **No guessing the project.** An explicit project wins. Otherwise the working folder must lie inside exactly one project's folder, the deepest match, or else in the same Git repository as exactly one project's folder. Two projects with the same folder, or no match, return the candidates and ask the agent to choose.
- **Locked memory cannot be changed by an agent.** Edits, replacement, archiving, invalidating and deleting are refused with a message pointing to `brain_create_proposal`. Agents cannot lock or unlock.
- **People decide when work is complete, and nothing that waits for them is missed.** Finished work always reaches the Review screen: with the agent's `brain_submit_review` report, or, when an agent only set the status (agents seldom write the report), with one Moah drafts from its checkpoints. Work that stops halfway for the person's OK reaches it too, as a question opened from the agent's waiting checkpoint; the person answers there or in the agent's chat (the agent's next checkpoint then settles it), approves it without words ("Approve and continue": the task goes back to in progress), or accepts it as done. Archiving with `brain_update_task` becomes a proposal; only `brain_archive_tasks` and `brain_archive_memories`, used when the person asked, archive directly. In the Review screen, accepting moves the task to Done and does nothing else (it records which acceptance criteria the person ticked; a line of the agent's report becomes a new task only when the person picks it), and sending back needs a comment and returns the task to in progress (recording only the criteria the person unticked). Accepted work can be reopened from Reviewed with a comment, which works like a send-back. The Review list shows one line per task; a task that is only Blocked, with no question asked, does not wait there. After a send-back: the next brief shows the comment, `brain_get_task` returns the whole review with the comment and attachments (text files inline, pictures through `brain_view_images`), and the Review screen can open Claude Code or Codex with a prompt for the fix typed in. Project Moah never starts an agent itself.
- **Agent writes are attributed.** Every activity event and agent-created record names the agent. Agent-created memory is unlocked and marked as agent-written.
- **Archived projects are read-only** for agents.
- **Search across projects** needs `scope="all"`, and its results are labelled by project.
- Context packs follow the safety rules in `ARCHITECTURE.md`: hidden, archived, replaced and unrelated records are never included, and manual-only memory only when named.
